## 2. Recommendation to the maintainer

**I disagree with `ready-for-agent` today, and I'd hold it.** Not on the merits of the behavior you
want — you may well be right that an empty report should print nothing. On the grounds that an agent
cannot land it under this repo's own rules.

The three findings, in order of how much they change the picture:

1. **The behavior is ratified, and the empty case is exactly what was ratified.** `render_brief(&[])
   == "Summary: 0 items\n"` is asserted in the contract suite, in a test named
   `brief_report_always_ends_with_a_summary_line`. This is not an unconsidered edge case that leaked
   out; someone wrote a test whose whole content is the empty input. `CONTRIBUTING.md` says contract
   assertions are ratified decisions, that changing one requires a superseding ADR, and that they are
   not touched during ordinary bug or feature work. So the fix is blocked on ADR-0003, which is your
   signature to give, not an agent's. An agent handed a naive brief would either edit the contract
   test (breaking the documented process) or stall.

2. **By the repo's own record this is an `enhancement`, not a `bug`.** A bug is behavior that
   contradicts intent; this behavior *is* the recorded intent. This isn't pedantry — per the
   out-of-scope rules, a rejected enhancement gets an `.out-of-scope/` record and a rejected bug
   doesn't, so the category decides whether a future duplicate gets deduped. Your call to overrule,
   but I'd log it as `enhancement`.

3. **Half of the reporter's argument is already answered.** The `wc -l` complaint is the machine
   consumer's case, and `--format json` already emits `{"items":[],"count":0}` with a doc comment
   saying that surface exists precisely for callers that shouldn't parse the human output. What
   survives is the aesthetic point — an empty report that prints a line reads as a result — which is
   real but weaker, and is the point ADR-0003 would have to stand on. ADR-0002 cuts against it by
   analogy ("terminal width is the terminal's problem"), so the ADR should say why the empty case is
   the renderer's problem and terminal width isn't. The strongest version of that argument: a report
   with no items has nothing to summarize, which is about the renderer's own semantics rather than the
   caller's environment.

Also worth knowing: the issue names `--brief`, but `render_full` behaves identically and carries its
own contract assertion. Fixing only brief leaves the two human surfaces inconsistent, which is a
second defect wearing a different hat. That's a design call, not an agent call.

**What I'd do:** label `enhancement`, hold the state at `ready-for-human` — the blocking unit of work
is writing ADR-0003, which is a design decision — and post the comment below. It does both jobs in one
shot so nothing waits on you twice: it records the verification and the blocker, and it carries the
complete agent brief, gated on the ADR. When you're back, answering the two questions at the end of
the triage notes (both surfaces or brief only; zero bytes or blank line) is enough for an agent to
draft ADR-0003 recording your decision and then do the work in a single pass. If you disagree with the
hold, nothing is lost: flip the label and the brief is already live.

One deliberate deviation from the brief-writing guidance: the guidance says not to reference paths,
because they go stale. This brief references `docs/adr/`, the `tests/*_contract.rs` glob, and the
CONTRIBUTING glossary. Those are directory conventions documented in CONTRIBUTING rather than source
file locations, and the ADR precondition is meaningless without naming where an ADR lives. No source
file path or line number appears in the brief.

## Agent Brief (gated — do not start until ADR-0003 exists in `docs/adr/`)

**Category:** enhancement
**Summary:** A report with no items renders no output at all; the summary line is emitted only when
there is at least one item.

**Current behavior:**
The brief renderer emits one line per item and then always emits `Summary: <n> items`. For an empty
item slice the summary line is the entire output, so an empty report is indistinguishable from a
result and always costs one line. The full renderer behaves the same way. The JSON surface already
represents emptiness as `{"items":[],"count":0}`. The empty-input behavior of both human renderers is
currently ratified by assertions in the contract suite.

**Desired behavior:**
Given an empty item slice, the brief renderer returns the empty string — no summary line, no trailing
newline, zero bytes. Given one or more items, output is byte-for-byte what it is today, summary line
included. The full renderer gets the same treatment if and only if ADR-0003 covers it. The JSON
surface does not change at any item count.

**Key interfaces:**
- `render_brief(&[Item]) -> String` — returns an empty string for an empty slice; unchanged otherwise.
  Signature does not change.
- `render_full(&[Item]) -> String` — same treatment, only if the ADR covers it.
- The dispatch function that maps a format to a renderer, and the `--format` parser, are unchanged.
- The JSON arm and its `{"items":[...],"count":n}` shape are unchanged, `count` included.
- The doc comment on the brief variant of the format enum currently promises "one line per item plus
  the summary line" — it must state the empty-input exception.
- The CONTRIBUTING glossary defines **summary line** as "the final line of a brief report" — it needs
  the same qualification.

**Acceptance criteria:**
- [ ] ADR-0003 exists in `docs/adr/` and supersedes the summary-line-on-empty decision, and the scope
      of the code change matches the scope of that ADR exactly.
- [ ] Brief rendering of an empty item slice produces zero bytes.
- [ ] Brief rendering of one or more items is byte-for-byte identical to today, summary line included
      — the existing multi-item contract assertion must pass untouched.
- [ ] The contract assertion covering the empty brief report is updated in place to the new
      expectation and renamed so it no longer claims the report "always" ends with a summary line.
      This is the ADR-backed exception to the "contract suites are not edited" rule: do not leave the
      contract suite failing, and do not add a duplicate test in another suite to route around it.
- [ ] The full renderer is either changed with its own contract assertion updated, or left entirely
      untouched — whichever ADR-0003 says. No partial state.
- [ ] JSON output is unchanged at every item count, including `{"items":[],"count":0}` for empty.
- [ ] Every non-contract test passes without modification.

**Out of scope:**
- The JSON surface, and the `count` field in particular. It is the supported way for a machine
  consumer to detect an empty report and it is not part of this change.
- Any new flag such as `--no-summary`. The decision is about what an empty report renders, not about
  giving callers a switch.
- The wording or format of the summary line when items do exist.
- Title truncation and anything else governed by ADR-0002.
- Exit codes and the behavior of any surface not named above.
